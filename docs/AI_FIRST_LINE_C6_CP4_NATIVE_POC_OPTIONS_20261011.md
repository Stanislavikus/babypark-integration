## Newly verified runtime/configuration feasibility and bounded alternatives (2026-10-11)

- **Private webhook/SSRF:** v4.18 source `lib/webhooks/trigger.rb#perform_request` calls `SafeFetch.fetch`; `lib/safe_fetch/fetcher.rb#perform_request` uses `SsrfFilter` for public-network-only URLs by default, optionally `PrivateNetworkRequest` when `SAFE_FETCH_ALLOW_PRIVATE_NETWORK=true`; default documented in `.env.example` line ~273. For a sandbox web hook on loopback or a private Docker network, first document the default block/agent-bot failure, then repeat with the **sandbox-only** native env flag enabled. This boolean disables the private-network SSRF barrier for that instance; it is **not** proof of a safe production private webhook architecture. Sources: exact `9f920b549c14491a4e587687a3eed5d21c6ccc7d`; Chatwoot issue https://github.com/chatwoot/chatwoot/issues/14489 .
- **Webhook failure path:** `lib/webhooks/trigger.rb` has retryable statuses `[429, 500]` only for AgentBot, and `update_conversation_status` calls `conversation.open!` after unhandled failure while `pending` unless `keep_pending_on_bot_failure` is set. Unsafe URL is a non-HTTP exception, so the failure handler can run without entering the normal HTTP response matrix. The PoC must first prove transport/URL routing before attributing a status transition to an HTTP code. No production enabling of account failure flag.
- **Compose merge:** official production Compose publishes loopback ports `3000, 5432, 6379` and has blank sample Postgres password. Docker documented merge appends non-identical ports; **`!override` requires Compose >=2.24.4**, or an independent standalone native-equivalent Compose, or `!reset` combined with validated port replacement. Require a redacted/structured `docker compose config` audit showing only `127.0.0.1:18082` (web) and zero host PG/Redis bindings; use a strong sandbox-only generated Postgres secret with no committed values. References: https://docs.docker.com/reference/compose-file/merge/ ; https://docs.docker.com/reference/compose-file/services/ .
- **OOM/swap/inodes/logging:** Compose `memswap_limit` must equal `mem_limit` to prohibit additional container swap; positive `oom_score_adj` biases host OOM against the test containers, but cannot guarantee catalog survives. Limit `pids_limit`, `logging.driver=json-file` and `max-size/max-file`. Monitor the first startup and DB migrations under hard caps and stop before competing for catalog memory. Source: https://docs.docker.com/reference/compose-file/services/ .
- **Native delayed rule:** v4.18 `app/models/automation_rule.rb#execution_delay_supported_conditions` explicitly forbids delayed `attribute_changed`; `config/features.yml` default false. Existing Native-R1 message_created delayed test remains a candidate; don't design a delayed priority-transition fallback.
- **Docker installation as host mutation:** official Engine + Compose installation is a separate, named action requiring explicit owner digest-bound permission and a complete before/after package, service, network/iptables, mount, process, port and Docker-objects inventory. Even when the rehearsal unit remains unchanged, host networking and daemon packages change. On unsafe coexistence, HALT, don't provision another paid server by implication.

## 2026-10-11 second independent review — refreshed native alternatives and scope

**Exact source:** `chatwoot/chatwoot` v4.18.0 at `9f920b549c14491a4e587687a3eed5d21c6ccc7d`; current BabyPark relay PR #128 `e4b6f136d47f12e09491ce697bc2919f88cd180a`. Review inputs: Opus 5.5 adversarial read-only review, Sonnet second-pass, independent current Git/source recheck. These are **source-level findings, not successful P1–P8 runtime results**.

- **Candidate A (SELECT as first experiment):** same Sidekiq container/namespace as native AgentBot job, ephemeral Ruby standard-library HTTP status responder on `127.0.0.1`, with sandbox-only SafeFetch private flag **in Sidekiq**, bounded by Sidekiq 512MiB / 0.5vCPU / pids96 and `SIDEKIQ_CONCURRENCY` configured via official `config/sidekiq.yml`. Lowest network complexity, zero new host ports/containers/runtime deps, but stub RAM competes with Sidekiq; STOP if memory bound approached or exceeded.
- **Candidate B (predefined bounded fallback, not a separate production choice):** ephemeral responder on Rails' **internal Docker interface** accessible as `http://rails:PORT` from Sidekiq; no host-published port, no additional container. Isolated bridge has no host IPv4 and tested negative host/metadata/public reachability. This shifts stub memory under Rails 800MiB cap but adds an internal inter-container listener; require explicit R0 connectivity/HMAC and negative egress retest. If neither A nor B is proven safe, HALT, never open the host bridge/proxy.
- **Native test harness alternative:** official Chatwoot API (inside container with synthetic auth) for post-bootstrap data operations where supported; dedicated static, reviewed synthetic fixtures are evidence/test scaffolding only, not production adapters. A previous account/team/rule fixture command was **blocked by provider safety checks**; do **not** tell the owner to manually SSH-run that denied command as a workaround or invent a different executor to evade the block. Pending a permitted execution path, P1–P8 remain NOT TESTED. Source/unit tests can be read-only.
- **E6 template class:** default `inboxes.enable_email_collect=true` can create **two** template messages on first incoming Website message when contact email is absent; greeting, OOO, CSAT also produce template under **different triggers**. `webhook_sendable?` admits template, and configured AgentBot can receive these. Run seven E6 transport cases with subtype annotations plus first-turn/mixed-event negative controls. Never assume all subtypes occur on initial arrival, nor infer the 3 observed messages' exact types without DB rows.
- **B1 relay response constraints:** current relay may return 422 for authenticated but non-admitted events and 503 on unknown authority, while Chatwoot may `open!` pending after non-retryable failed webhook. `open` with `SAME_AGENTBOT` **is not completed HUMAN handoff**. `503` may be an appropriate fail-closed *semantic decision* (zero BabyPark unsafe write) but is **not** guaranteed operator notification or durable continuation. `2xx` only for positively classified/verified ignored events; invalid signature `401` on BabyPark boundary does not prevent Chatwoot's own non-2xx failure side effects. Unknown signed provenance continues deny/fail-closed, never silently 2xx.
- **Retry/log privacy:** Chatwoot `AgentBots::WebhookJob` logs `payload.to_json` on retryable 429/500; payload includes `content` and may carry attachments. Recommending 500 as generic substitute for 503 is therefore **REJECTED**. Merely keeping 503 does not prove all other Chatwoot logs are PII-free; production log access/retention controls and HTTP timeout are separate acceptance gates.
- **Native mention limits:** `conversation_mention` in-app notification is possible for eligible inbox members/admins, but initial AccountUser settings enable only **conversation_assignment** email/push. Seller-specific mention notification preferences and device subscription are separate production/user acceptance. Real device push (P8), UI operation and operator ACK **NOT TESTED** in this no-external/no-host-port PoC; production acceptance is separately gated.
- **Durable operations:** `docs/AI_FIRST_LINE_DESIGN.md` §29.8.2 requires durable BabyPark operator-attention/health fault in addition to HUMAN continuation after unresolved handoff. Native Chatwoot delayed at-most-once and shared Sidekiq/Redis dependency **do not satisfy it**. The native rule minimum is 10 minutes, and stock `TriggerScheduledItemsJob` runs every five cron minutes to enqueue pending executions: nominal due-time plus next sweep is not a measured delivery SLA, particularly under worker backlog. With `delayed_automations` disabled on an Account, scheduling silently skips; test gate must positively assert feature enabled. A simple read-only route is not sufficient without the durable condition and measured escalation. Any implementation or normative contract amendment requires its **own** §1–§3 gate, not a silent relaxation in this PoC.
- **Production-only information (NOT VERIFIED):** whether the actual EE Website inbox uses Captain, Email Collect, greeting/OOO/CSAT, its SafeFetch/private flag, bot `outgoing_url`, seller push/email settings, and selected public HTTPS relay. Never change production inbox settings or tell the operator to disable Email Collect without separate UX/owner choice and operational gate.
