## New candidate risk gate — no assumptions

The Website Widget route is **not the previously rejected untrusted public API Inbox**. It requires an already issued per-website signed `X-Auth-Token`, is constrained by the WebWidget Inbox, and can create one message/conversation. It also has its own risks: anonymous visitor creation, rate limiting/abuse, possible signed-cookie exposure from same-origin scripts, transport CORS, Rails and nginx PII/request logging, existing visitor conversation labels, webhook delivery, retry duplication, token expiry, third-party JS, CSRF, same-message traffic, notifications, and future Chatwoot upgrades. Existing widget contact identity APIs also invoke ContactIdentifyAction; never claim the entire Widget API is free of identity/merge risk. Show the new route is not *adding* a new wider public-contact mutation capability; verify exact accessible methods.

**Known requirements before implementation selection:** confirm supported/upgrade-safe external use of the endpoint (if unsupported, downgrade to `PoC-only` / STOP), evaluate precise Nginx CORS preflight scoped to one endpoint and only the BabyPark website Origin, HMAC/JWT token provenance, callback phone/form rejection/optional text, same-contact existing conversation label/team behavior, delivery acknowledgement, throttling, bot/duplicate response, logs/webhooks and safe rollback, all with synthetic-only data first. Cross-account side effects and production personal data are forbidden for proof.

This docs-only scan selects **bounded evidence, not a production implementation**. A changed candidate, runtime version, license, trust boundary or material constraint requires a new SHA-bound Scan and Fit before any production-code stage. No site, Chatwoot, Nginx, DNS, account, credential or running container changed.
