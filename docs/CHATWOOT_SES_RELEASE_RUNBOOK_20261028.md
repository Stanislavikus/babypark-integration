## Incident path (NOT default rollback)

For a serious active ingress incident where receiving itself is unsafe: stop future outgoing first, drain jobs, explicitly obtain incident authorization (or established on-call break-glass policy), then use **a pre-tested separate SES receipt rule set with a BounceAction** for the exact reply domain. Sender must be SES-verified, message must clearly instruct buyer to use a live verified alternative. This deliberately rejects replies and therefore loses that communication; send an operator incident notice and plan for recovery. AWS only permits one active receipt rule set in the region. Never silently activate an untested or broad rule set.

For Chatwoot temporary outage: leave receiving on; SNS native retries are bounded and then DLQ retains failed-to-deliver SNS notifications for four days. If Chatwoot already returned 204, **there will not be an SNS retry/DLQ copy merely because downstream Sidekiq later failed**. Locate the exact `ActionMailbox::InboundEmail` by its internal ID, Message-ID/checksum and lifecycle state, confirm its protected raw-email ActiveStorage blob, and correlate the `ActionMailbox::RoutingJob` in all Sidekiq states. `pending` / `processing` / `failed` are not equivalent to `delivered`; do not blindly change status or bulk replay. Re-enqueueing the stock routing job is permitted only under a proven isolated procedure, identity/duplicate checks and an authorized incident runbook. Where record/blob or downstream commit state is uncertain, HALT and escalate.

## Read-only recovery and retention facts (source-verified 2026-10-28; **not** a recovery drill)

- Installed Chatwoot v4.18.0 uses `aws-actionmailbox-ses 0.1.0`. The signed SNS controller's `create` stores `ActionMailbox::InboundEmail.create_and_extract_message_id!(notification.message_content)` and only then returns HTTP 204. After-save `route_later` schedules `ActionMailbox::RoutingJob` in the separate `action_mailbox_routing` queue. A 204 proves ingress acceptance, not a Chatwoot message commit.
- `ActionMailbox::InboundEmail` persists the raw MIME via ActiveStorage; the native uniqueness index is `(message_id, message_checksum)`. `ReplyMailbox` uses a DB transaction around message and attachment creation; `MailboxHelper` checks an existing conversation message `source_id` first. Those mechanisms are **source evidence, not demonstrated exactly-once behavior** under post-commit failures, retries or concurrency. S5 remains OPEN.
- Rails `actionmailbox 7.2.3.1` defaults to `incinerate=true`, `incinerate_after=30.days`; processed `delivered/failed/bounced` records schedule a native incineration job in `action_mailbox_incineration`. The incineration job deletes a due, already processed record (its associated raw blob follows ActiveStorage lifecycle). Records remaining `pending/processing`, failed incineration jobs, backups, delivered Chatwoot transcript/attachments and external mail provider copies **do not have a proven global 30-day maximum**. Verify effective runtime overrides, actual incineration success, retention policy and restore windows before activation.
- Read-only AWS confirmation in Frankfurt: no active SES receipt set; prepared `website-reply-uuid` disabled; SNS HTTPS subscription confirmed with 63 configured retries and SQS DLQ; DLQ `MessageRetentionPeriod=345600` (4 days), approximate visible and in-flight messages 0 at the read. A DLQ empty count is not evidence about post-204 handling or historical deliveries.
- Privacy/access inventory to sign before customer activation: (a) SES/SNS transient delivery and four-day SQS DLQ, (b) ActionMailbox raw MIME / ActiveStorage / related DB states, (c) resulting Chatwoot transcript and message attachments, (d) chatwoot-host and cloud backups, (e) agent/admin access and diagnostic logs, (f) recipient/provider email copies. For each confirm real controller, access, legal basis/notice, lifecycle/expiry, deletion and incident recovery; no new BabyPark mail archive or diagnostic PII. Production customer activation remains HALT until the owner/privacy approver confirms the whole matrix.
- Separate identity observation: `ContactIdentifyAction` and Website widget contact/conversation controllers on installed v4.18.0 match official release Git blobs; all three are unchanged in upstream v4.19.1. The source merges same-email contacts under defined identifier conditions, while unverified old-conversation listing is scoped to the requesting `contact_inbox`. **No production cross-contact attack or reading of A's old conversation was performed/proven.** Upstream #16186 remains a separate Website/contact integrity investigation; do not present it as an SES regression.
