## A. Single target architecture — design choice for analysis, NOT an implementation selection

Retain native **Chatwoot v4.18.0 AgentBot signed webhook + official exact-message REST reader + Node built-in HTTP/HMAC + existing `FirstLineStateStore` v4 + SQLite**. No new database, broker, service, runtime dependency, paid SaaS, Chatwoot core fork, public AI POST or transcript storage. Exact component/version alternatives and any new code-stage fit/scan must be freshly bound under Agreement §§1–3 **after** the remaining evidence is available; this planning note alone selects no production implementation.

**One ingress OS process and Node event loop at most**, including rolling restart/replacement. At admission: finite positively configured `N`, body size/deadline, maximum total admitted work over a bounded window, bounded rejection/slow-body resource cost and cumulative callback/replenishment control; fail-closed on missing proof. One signed locator -> **one exact authoritative Chatwoot REST GET** with an evidence-derived bounded request timeout and no speculative source proof -> one **synchronous owning write transaction** encompassing source-key equality/dedup, stream existence/creation, event insert, revision/deferred-parent/continuation/HUMAN fences -> bounded ACK or deny/error. No other preliminary SQLite read transaction before the owning write transaction; move necessary read authority under that single owning transaction, after authoritative REST. Never `await`/yield or accept a thenable inside `tx()`. No customer-facing AI send/handoff is authorized by an ingress ACK.

Current contrast: ingress already validates signed locator and does an exact reader call, but performs preliminary store reads and separate `ensureConversationStream` / `ingestConversationEvent` operations, with no body-read deadline or admitted-callback count: [src/copilot/first-line-runtime-ingress.mjs:54-69](https://github.com/Stanislavikus/babypark-integration/blob/927c19dee09d4ce581f8de6c619b1d29c591d239/src/copilot/first-line-runtime-ingress.mjs#L54-L69), [src/copilot/first-line-runtime-ingress.mjs:71-121](https://github.com/Stanislavikus/babypark-integration/blob/927c19dee09d4ce581f8de6c619b1d29c591d239/src/copilot/first-line-runtime-ingress.mjs#L71-L121), [src/copilot/first-line-runtime-ingress.mjs:145-166](https://github.com/Stanislavikus/babypark-integration/blob/927c19dee09d4ce581f8de6c619b1d29c591d239/src/copilot/first-line-runtime-ingress.mjs#L145-L166), [src/copilot/first-line-runtime-ingress.mjs:188-205](https://github.com/Stanislavikus/babypark-integration/blob/927c19dee09d4ce581f8de6c619b1d29c591d239/src/copilot/first-line-runtime-ingress.mjs#L188-L205). ## D. Structural `K` derivation for the *future* single-transaction path

Under a **proposed, conditional** journal mode DELETE + **verified per-connection** `PRAGMA cache_spill=OFF` and bounded dirty-page/cache/memory safety, and with no external SQLite work sharing the ingress event loop:

1. **One `BEGIN IMMEDIATE`** for the atomic source-key/stream/event/HUMAN operation: one potentially blocked RESERVED/write acquisition site (`K_begin=1`). Do not frontload a separate SQLite read-transaction.
2. **One DELETE-mode `COMMIT`**, which can need to wait for readers before acquiring EXCLUSIVE (`K_commit=1`). Both wait sites require their *own ingress-connection* read-back `B_ingress` and independently evidenced polling/scheduling overshoot.
3. **Spill-induced statement-level EXCLUSIVE acquisitions:** `K_spill=0` **only if** `cache_spill=OFF` is verified and the actual chosen workload has no other re-acquisition path; if ON/unknown, dirty-page/statement-level work needs an explicit finite proven site count. Do not claim the ON stress-test's 3.045 s is typical ingress. This is a **conditional proposed choice**, not a code/config change or adopted journal mode.

For **one successful target transaction**, `K_single_tx_candidate = K_begin + K_commit + K_spill = 2` under those conditions and absent further native SQL acquisition sites. **This 2 is a structural candidate, NOT a measured upper bound for every error path nor the entire event loop**. Inventory exception/rollback/retry, triggers, engine/cache behavior, checkpoint/migration/backup, and verify SQLite-version-specific site semantics before treating the candidate as an enforceable bound. If required new sites are found, amend the model and re-review; no auto-success.

For a callback's **response budget**, count every potentially blocking SQLite acquisition on the SAME event loop that may delay it: its own transaction, transactions from other admitted callbacks and repeated admission/resume cycles, plus any co-resident non-ingress connections proven present. The overall `K_total` requires a **finite bound on total work/replenishment within the response window**, not `2×N` guessed from simultaneous admission. The design must provide deterministic limits on admitted work/rejection and account for different site-specific timeouts. Let `A_max` be the evidenced maximum owning transactions able to execute ahead of/while blocking one response and `K_extra` the proven other same-loop sites: only after closing workload/queue/arrival gates is `K_total ≤ 2·A_max + K_extra` a justified *conditional* successful-transaction envelope; error paths contribute separately. `A_max`, `K_extra` and abort-path count remain **UNKNOWN**, not zero.

For external-process recovery/backup lock holding, account their actual lock competition, I/O and impact on `B_wait`/response latency without substituting the other connection's 5000 ms into ingress's `B_site`. Independent process and journal-mode eligibility must be proved before exclusion.
