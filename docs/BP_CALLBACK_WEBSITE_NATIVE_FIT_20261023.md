## Product outcome and non-negotiable acceptance

The *already installed and operational* `babypark.ua` launcher gets one `Зворотний зв'язок` choice directly below `Зателефонувати`, rendering phone input (required, Ukrainian `+380`, digit-focused, rejects letters/pasted junk and invalid final length) and optional comment (blank accepted) in the same anchored panel. `Замовити дзвінок` creates a Chatwoot conversation/message assigned to `Продажі`, labeled `callback`. Only after server-accepted response report `Заявку надіслано`; failure or lost ACK must never promise success or blindly retry duplicate request. No time picker, no second Chatwoot Account, no additional durable phone store, no fake callback button, no auto-dial. Avoid Chatwoot Website SDK loading when opening menu or selecting Telegram/Viber/direct phone; it may load only after explicitly selecting Chat or Callback.

## Selected architecture and source-backed limits

**Best candidate** (not yet final accepted production option): continue using the **existing Website channel and its signed widget token**, not new public Channel::Api inbox. On explicit Callback user choice, lazily start the stock Website SDK using the already configured public Website token; once `chatwoot:ready` fires, the SDK writes its signed `cw_conversation` cookie in the same-origin website document. On explicit validated Submit, the frontend may read *only that existing token in volatile memory* and send **one** `POST https://chat.babypark.ua/api/v1/widget/messages?website_token=<public_token>` with `X-Auth-Token=<widget JWT>` and `message.content` containing a fixed callback marker, normalized phone and optional comment (only if provided). `custom_attributes.callback_phone` and `labels:[callback]` are supported by the stock message controller only on *new* Conversation creation; existing conversations require a proved label/routing step, potentially official SDK `setLabel` after a saved message or stock message-based Automation. **Treat label assignment/async Sales routing unknown until tests pass.** Do not log/reuse/publish JWT, and do not write a second PII state store. No API Inbox, no public API Inbox identifier, no separate Contact phone update and no external backend is needed if these assumptions are validated.

**Version/source facts:** stock upstream exact `app/controllers/api/v1/widget/messages_controller.rb` blob `c4fd9c82027a5a5fa9987a8af25a789c374d8b15`; `app/controllers/api/v1/widget/base_controller.rb` blob `90f3728fbf5ce6597a592935bd5d4f146f9ae434`. Deployed rehearsal v4.18.0 `app/controllers/concerns/website_token_helper.rb` uses `X-Auth-Token` decoded through `Widget::TokenService` then contacts resolved to WebWidget's own inbox. The Browser Widget uses this internal endpoint in `app/javascript/widget/api/endPoints.js`; it is **not documented as a public SDK send API**, and external usage may be unsupported or brittle. A written supported upgrade/compatibility check and independent review are required; if not achieved, STOP rather than claim an official API contract.

**Production Nginx requirement, if proven fit:** `chat.babypark.ua` Nginx 1.20.1 currently has a general `location /` proxy; a dedicated precise `location = /api/v1/widget/messages` with conditional CORS support for `https://babypark.ua` / `https://www.babypark.ua` can allow browser requests with `Content-Type` and `X-Auth-Token` without globally enabling `ENABLE_API_CORS` or changing Chatwoot core. Preserve same-origin widget GET/POST and deny no legitimate Chatwoot widget behavior; preflight OPTIONS must not create or mutate objects; correct `Vary: Origin` and no credentialed wildcard; preserve proxy auth header, TLS SNI, error semantics. All incoming native widget endpoints are already externally addressable; the CORS rule itself is not authentication and MUST NOT be counted as an anti-bot/security proof. Narrow rate controls must never degrade ordinary Website chat. Requires staged Nginx `-t`, synthetic request headers, negative origin tests, rollback, and separate live-change GO.

**Hard limitations:** internal endpoint upgrade compatibility UNKNOWN; no durable exactly-once request key on stock Widget messages (one call narrows but does not solve duplicate/lost ACK); label applies only when creating a conversation, not to existing visitor conversation; account-wide identity/merge operations of other Website contact APIs are *not* declared safe; browser token is bearer identity, subject to malicious JS/XSS; JS input filtering insufficient for trusted server validation; text in Chatwoot request may appear in application/proxy error logs/webhooks if configured. Need source/routing proof for notifications, sales access and no extra PII copy. Generalized global CORS and same-origin reverse proxy are *not* assumed safe fallback.
