## Causal status
**Proven:** installed sidekiq_alive forks its GServer-based healthcheck; the code can spin forever on incomplete/early-closed HTTP header input. The observed hot `gserver.rb:264` Ruby child thread and cgroup CPU baseline are strongly consistent with this loop. **Not proven:** precise live thread Ruby stack, that a specific client prematurely closed a connection, how frequently it happens, source of such a connection, or that any workaround will restore idle CPU. Do not call the root cause certified based only on static reasoning plus OS thread name.
This diagnostic does not itself authorize reaching the liveness endpoint, modifying HTTP healthchecks, reading socket tables/IPs, sending signals, killing a child, deploying a Puma handler, appending env vars, restarting the worker, patching Chatwoot core, or writing production code.
