## Purpose, method, selection
Native Node24.20.0 built-ins (node:http, node:crypto, node:sqlite, perf_hooks, node:test/standard assertions); no npm/apt, new production runtime or new hosting. Existing Linux process tools for pre/post. Tests execute only on existing babypark-catalog-rehearsal-fra1 (DO-Premium-Intel, 2vCPU, 3.8GiB RAM, ext4) using existing /opt/babypark-rehearsal/runtime/node-v24.20.0/bin/node, SHA-256 89af8424dd53e560b1933f87ba650d8bf57c83ca5a04600eefb31f416aabbae7, Node v24.20.0/SQLite v3.53.4. Loopback is NOT exposed: the synthetic Node HTTP server uses a private UNIX-domain socket owned by unprivileged test uid in disposable /tmp inside an unshare --net network namespace. No production Chatwoot, credential, API connection, public TCP port or customer text, no network routes, no production host telemetry, no Chatwoot containers/startup, no package installation. No runtime src changes and no merge. A synthetic HTTP mock is only an experimental surrogate, not Chatwoot v4.18.0 native effects.

Experimental parameter choices BELOW are limited functional experiment stimuli, not proposed C6 runtime limits, customer callback budgets or an approved production SLO:
- Simulated callback/body bytes <=4096, JSON payload length <=256 bytes, HMAC-SHA256 with synthetic fixed key. Synthetic service rejects invalid HMAC=401, oversized body=413, slow/incomplete body=408, over-N requests=503 (these HTTP statuses are NEVER asserted safe for actual Chatwoot). A 30-ms synthetic body timer and 80-ms delayed client chunk exercise rejection behavior; no assertion of interruptible JS scheduling. Unsupported unknown event fails closed. A synthetic mock authoritative read is 3 sequential await phases of 6-ms timer latency; 3 reads are experimental stimulus only, **not** a measured Chatwoot read-count bound. No external reads whatsoever.
- One synthetic HTTP OS process/event loop, concurrent in-flight admission **N=4** and test-only total per-wave arrival **8**, with immediate fifth-plus rejection; a separate series uses 32 total arrivals in four sequential bounded waves of eight to expose replenishment. Test caller and server run on the SAME 2 vCPU and share CPU/scheduler; charge that contention as experimental, NEVER subtract it or claim uncontended ingress performance. Work-resume upper count test-only: at most 32 successful admission starts across four waves, 3 timer resumptions per successful request plus 64 synchronous SQLite SELECT statements in each admitted request; hard synthetic workload cap 32*64 statements and 32*3 timer resumes. This deliberately exaggerates co-resident synchronous cost without proving production `C_sync` or event-loop `K`.
- For A2, use existing actual v4 FirstLineStateStore for immutable metadata ingest plus DIRECT_HUMAN cut and continued AI refusal, each measured case creates its own synthetic stream in a pre-created schema-v4 temporary store. 10 warm-ups followed by 59 individually measured cases. Current v4 requires two transactions for stream creation + event append; this is **surrogate** for future one-transaction ingress.
- For normal accepted HTTP latency (no backlog), 10 warmups + 59 measured sequential single requests; report raw end-to-end local UNIX socket durations, nearest-rank p50/p95, max, mean, and event-loop delay raw monitor summary. Each successful synthetic reply must be HTTP 200 with a literal `synthetic:true` acknowledgment (NOT a real Chatwoot 2xx response).
- For overloaded wave (8 simultaneous), 10 warmup waves plus 59 measured waves; assert that at most four requests are admitted, the others return synthetic 503, all synthetic responses terminate; report raw per-wave latency and counts. Four sequential waves of 8 (32 total) are executed 10 times as separate bounded functional checks for replenishment; require exact accounting and prevent silent increase in admitted work. A dedicated 59-trial co-resident-SQLite scenario adds 64 same-event-loop SELECT statements per accepted reply under 3 sequential timer resumes; monitor delayed response and resumption counts and report raw arrays. This remains observational: event-loop Q and SQLite sync work are not double-counted as independent budget components.
- For slow body, oversized body and invalid HMAC, do 10 negative functional trials each; expected 408/413/401 respectively and zero mock REST calls for those requests. Slow-body client waits 80 ms before final chunk and response deadline is 30 ms; client errors after server close are recorded, never re-labelled as success. Tests have a single outer 180-s wall-clock timeout.
