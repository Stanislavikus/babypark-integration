## 1. Решение

**Выбран вариант B: отдельная OEM-стадия строит подтверждённые отношения; V4.2.1 их потребляет.** Производитель присылает ≈20 названий моделей → названия разрешаются в идентификаторы моделей через реестр и явные алиасы → из проверенных утверждений строятся отношения «модель × аксессуар (× рама)» в одном из четырёх состояний → V4.2.1 берёт готовые отношения через тонкий шов и применяет к ним **свои существующие** гейты (покупаемость, профиль вариантов, порядок, лимит 20, инварианты `similar`) → существующий Stage1 → публикация.

Новый производитель или аксессуар — это **только данные**: документ, утверждения, привязки. Код матчера не меняется.

Почему не A и не C — раздел 2. Главное: A повторяет путь PR #167 и вынуждает V4.2.1 нести ответственность, которая ей не принадлежит (проверка документов, идентичность, условия); C добавляет хранилище и общность, которых запрет «вывод по типу интерфейса — не доказательство» сегодня не позволяет использовать.

## 3. Целевой поток

```
OEM-документ (URL, HTML/PDF)                     [данные, собираются по мере появления производителей]
   │  O1  сохранить байты → sha256 → запись oem_document (регион, язык, версия, дата)
   ▼
oem_claims  PROPOSED ──(проверка якорей цитат + утверждение человеком)──► VERIFIED
   │  O2  имена из утверждений → model_id (реестр + явные алиасы; точное равенство ключей)
   │  O3  артикул производителя → SKU каталога (явная привязка с основанием)
   ▼
O4  построитель отношений: LISTED / LISTED_CONDITIONAL / EXCLUDED / UNKNOWN
   ▼
oem_relations.json  +  oem_vs_current_report.json   ◄── этап 1 (shadow): V4.2.1 НЕ меняется
   │
   │  шов в V4.2.1 (этап 2): build_catalog(..., oem_relations=…)
   ▼
кандидаты A_model (reason = accepted_oem_relation) → существующие гейты V4.2.1 → существующий Stage1 → публикация
```

Правила потока (каждое — ответ на конкретный дефект):

1. Стадии O1–O4 — детерминированные функции от входных файлов; повторный запуск даёт байтово тот же результат.
2. Матчер ничего не знает о Stage1: Stage1 привязан к **цели** (nid, vid, option_digest, язык) и остаётся в своей downstream-стадии. Публикация = кандидат OEM ∧ Stage1(цель) ∧ Stage1(контекст источника) (C4, C5).
3. AI может создавать только утверждения `PROPOSED`. Отношения строятся из `VERIFIED` (P5).
4. Идентичность — равенство идентификаторов моделей, а не сравнение текста (E1–E3, P2).
5. Условия переносятся, но сборкой не вычисляются (P7).

## 4. Минимальная схема данных

Файлы JSON/JSONL рядом с остальными входами V4.2.1 (`engine/input/`); никакой новой БД. Хранение байтов документов — каталог, где имя файла = sha256 содержимого (проверка целостности — пересчёт хэша); место (git или артефакт-хранилище) — решение владельца OD7.

### 4.1. Сущности

| Сущность | Назначение | Ключевые поля |
|---|---|---|
| `oem_document` | Одна версия одного документа производителя | `doc_id` (= sha256 байтов), `url`, `manufacturer`, `region`, `language`, `doc_version` (как указано производителем), `retrieved_at`, `supersedes` (doc_id или null), `content_type`, `size_bytes` |
| `oem_claim` | Одно утверждение из документа | `claim_id`, `doc_id`, `relation_type` (`accessory_for_model` / `adapter_between` / `vehicle_general`), `accessory` (`brand`, `oem_article`), `completeness` (`exhaustive_list` / `partial_list` / `unspecified`), `targets[]` или `frames[]` (см. ниже), `conditions[]`, `variant_policy` (данные, как в легаси-правилах), `quote` (`text`, `char_start`, `char_end`), `status` (`PROPOSED` / `VERIFIED` / `REJECTED`), `extracted_by` (`human:…` / `parser:имя@версия` / `llm:модель@версия`), `verified_by`, `verified_at` |
| `model_registry` | Идентификаторы моделей и их алиасы | `model_id`, `brand_tid`, `family`, `generation`, `successor_of`, `variant_of`, `keys{lang → ключ}`, `in_catalog`, `aliases[]` |
| `model_alias` | Явное соответствие строки модели | `alias_id`, `model_id`, `text` (как есть, с кодовыми точками), `script_profile`, `lang`, `origin` (`oem_doc` / `catalog_title` / `reviewer`), `reviewed_by`, `reviewed_at`, `status` |
| `catalog_binding` | Артикул производителя → SKU каталога | `binding_id`, `brand`, `oem_article`, `catalog_sku`, `basis` (`gtin` / `brand+mpn` / `reviewed`), `evidence_ref`, `status`, `reviewed_by` |
| `condition_types` | Словарь условий | `type`, `evaluable`, `context_keys`, `unit`, `label{ru, uk}` |
| `oem_policy` | Параметры политики (данные) | `allowed_regions`, `allowed_languages`, `ttl_days`, `publish_states`, `one_ended_adapter`, `veto_mode`; пустая политика = ничего не публикуется |
| `oem_relation` (**производная**, не источник истины) | Результат O4 | `relation_id` (= sha256 канонического JSON записи), `accessory_sku`, `source_model_id` (для адаптеров ещё `frame_model_id`), `fit_state`, `conditions[]`, `claim_ids[]`, `doc_hashes[]`, `binding_ids[]`, `registry_version` |

**Структура целей.** Для `accessory_for_model`: `targets[]` = `{name, polarity}`, где `polarity` ∈ `listed` / `explicit_absent` / `explicit_reject`. Для `adapter_between`: `frames[]` = `{name, seats[]}`, где `seats[]` = `{name, polarity, conditions[]}` — **списки кресел по каждой раме**, как их и публикует производитель; пары (рама, кресло) выводятся при сборке. Структурные квалификаторы вида «только с рамой X» выражаются самой структурой списков, а не текстом.

### 4.3. Алиасы и идентичность — правила

1. **Один нормализатор.** Рекомендуется закрепить легаси `canonical_models.key()` (L38): он уже определяет модель во всём каталоге V4.2.1, поэтому OEM-привязка согласуется с существующей идентичностью. Нормализатор PR (`normalize_oem_model_span`, L303) в OEM-путь не переносится; его негативные кейсы используются как тестовый оракул. Контракт — матрица равенств N1 (`PR167_ARCHITECTURE_GAPS.md`, раздел 6), закреплённая тестом T2.5. Это решение подтверждает владелец (OD8).
2. **Автопривязка только по точному равенству ключей** внутри бренда. Токены поколения (`Pro`, `Pro 2`, `Cub`, `5`, `Renew`) не отбрасываются; подстрока, префикс и «продолжение» — не соответствие.
3. **Не привязывается автоматически, а идёт в очередь ревью** со своим кодом причины: нет совпадения (`no_match`); несколько совпадений (`multi_match`); смешение скриптов в строке (`mixed_script`); совпадение skeleton по UTS #39 с **другим** ключом (`skeleton_collision`); слеш-сокращение или скобочная форма (`shorthand`, например `Pebble 360/PRO(2)`).
4. **Алиас — запись данных с ревью**, действует на уровне модели: все страницы, SKU и языки этой модели (не на уровне NID).
5. **Модели, которых нет в каталоге**, сохраняются (`in_catalog: false`) и становятся активными, как только модель появляется в каталоге — без правки утверждений.
6. **Детектор двойников** (UTS #39) только поднимает задачи ревью; skeleton не хранится и не служит ключом.
7. **Исправление заголовков каталога** (`М` → `M` в источнике) — отдельная задача данных; алиас остаётся временным механизмом.
8. Связи поколений (`successor_of`, `variant_of`) используются для отчётов и для **предложения** кандидатов в отрицания; совместимость по ним не выводится.

### 4.4. Привязка артикула к SKU

Основания — по лестнице доказательств репозитория (`docs/PRODUCT_IDENTITY_RESOLUTION_V1.md`): `gtin` (когда экспортёр начнёт его выгружать) > `brand+mpn` (точное равенство артикула производителя и SKU/MPN каталога с проверкой бренда) > `reviewed` (подтверждено человеком с доказательством). Совпадение по заголовку, цене, коду продавца или копии на другом языке основанием не является (`STAGE1_REQUIREMENTS.md`). Пример: `Relax Insert` — артикул производителя `ACCSFCC207` не привязан к SKU каталога `2000040775` → отношение не строится, создаётся задача ревью.

### 4.5. Размер ревью

Ревьюер видит diff утверждений: автопривязанные по точному ключу имена показаны рядом с названием модели каталога; очередь содержит только непривязанные, неоднозначные и условные записи. Время ревью на аксессуар в этом исследовании не измерялось.

## 5. Четыре состояния и правила вывода

Состояние определяется для пары (модель-источник × аксессуар); для адаптеров — для тройки (кресло × адаптер × рама), с производными индексами по каждому концу. **Ни одно состояние не является утверждением безопасности.** Допустимая формулировка: «Производитель указывает совместимость с моделью X; условия: …».

| Состояние | Когда | Что делает V4.2.1 (этап 2) |
|---|---|---|
| **LISTED** | Есть актуальное утверждение `VERIFIED` с `polarity: listed` для этой модели; условий нет | Кандидат `A_model` (`reason: accepted_oem_relation`); дальше существующие гейты и Stage1 |
| **LISTED_CONDITIONAL** | То же, но есть условия (вычислимые и/или `display_only`) | Кандидат с `fit_state` и `conditions[]`; **удерживается** (в отчёте), пока `oem_policy.publish_states` не включает это состояние (решение OD4: формулировки ru/uk) |
| **EXCLUDED** | Актуальное утверждение `VERIFIED` с `explicit_absent` или `explicit_reject` для этой пары; либо конфликт двух актуальных утверждений (в сторону отказа, с флагом конфликта) | Вето: убирает текстовую ссылку `A_model` для этой цели и блокирует `B_universal`. Режим `report` (по умолчанию) только фиксирует; `enforce` — по решению OD3 |
| **UNKNOWN** | Нет утверждений; модель вне **неполного** списка; нет привязки артикула; непривязанное или неоднозначное имя; не подтверждены оба конца адаптера | Ничего; причина — в отчёте и очереди ревью |

Правила вывода:

1. Приоритет: EXCLUDED > LISTED_CONDITIONAL > LISTED > UNKNOWN. Вето даёт **только явное** отрицание; отсутствие в списке само по себе — UNKNOWN (P6).
2. Учитываются только `VERIFIED`-утверждения документов в допустимых регионах/языках (`oem_policy`), не заменённых более новой версией (`supersedes`) и не просроченных по `ttl_days` (просроченные помечаются `stale`; поведение — OD2).
3. Для адаптеров по спискам рам и кресел строятся индексы по каждому концу: страница кресла получает отношение с условием «рамы: [список производителя]», страница рамы — с условием «кресла: [список производителя]».
4. Для одноконцевых страниц публикация адаптерных отношений регулируется `one_ended_adapter` (OD5). По умолчанию — `abstain`: `STAGE1_REQUIREMENTS.md` требует трёх узлов и воздержания, если коляска не выбрана или неизвестна. Данные хранят полное тернарное отношение в любом случае; меняется только политика показа.
5. `reject_condition` (условие не выполнено у конкретного покупателя) в сборке не существует: условия переносятся, вычисляет потребитель с контекстом (D3 в `PR167_ARCHITECTURE_GAPS.md`). Вычислимые предикаты закрываются небольшим универсальным вычислителем по словарю типов; он нужен только потребителю с контекстом покупателя и не входит в минимальное изменение сборки.
6. Класс C (`vehicle_general`) модельных отношений не порождает.
7. Статус стадий и причины воздержания — коды из приложения B `PR167_ARCHITECTURE_GAPS.md` (словарь причин ревью).
