1. BOUNDED STAGE

C6-P1 changes only the durable semantic/state-store concern required by the
merged C6/C25 v0.8 contract. This stage may change FirstLineStateStore schema,
migration, state transitions, validators and owned tests/traceability.

Explicitly OUT OF SCOPE for C6-P1:
- Chatwoot public POST/send client;
- S1/S2 network orchestration and final Chatwoot current-conversation read;
- extraction producer / LLM;
- scheduler/timer/worker deployment;
- automated Chatwoot handoff write;
- operator-attention transport;
- C25 dependent routing and shared matcher patch;
- production activation/cutover.

2. COMPLETE APPLICABLE REQUIREMENTS / FIT TEST

P1-R01 — episode.sqlite remains the single durable semantic owner; no second
durable workflow/state truth may become authoritative.
P1-R02 — additive, explicitly attested schema evolution from current schema v3;
runtime open must not silently auto-migrate. Production migration itself requires
a verified backup before execution.
P1-R03 — one immutable semantic origin per committed stream revision:
PUBLIC_ACTION(action_id), DIRECT_HUMAN or NON_ACTIONABLE_ACK.
P1-R04 — PUBLIC_ACTION origin/action provenance is permanent; fail-closed execution
may attach monotonic durable HUMAN continuation but must not replace/replan origin.
DIRECT_HUMAN, NON_ACTIONABLE_ACK and HUMAN continuation are absorbing for autonomous AI.
P1-R05 — prepared public action durably stores non-dynamic descriptor/provenance
required by v0.8, including public reason/template_id/response_locale and complete
canonical semantic scope actually consumed by C4, with relational provenance.
Dynamic price/stock/policy/hours/labels/rendered payload and customer raw/normalized
text/content digests remain forbidden durable state.
P1-R06 — MONEY scope is exact UAH when a bound exists, nullable non-negative safe
integer min/max, zero representable, min<=max, with provenance; invalid/mixed shapes
fail closed.
P1-R07 — customer-event acceptance while same-stream action is SENDING/UNCERTAIN
atomically commits accepted event + stream revision + immutable deferred-parent
action relation in the same owning-store transaction; relation is scheduling only.
P1-R08 — same-revision action failure cannot silently orphan semantic work as
STALE/CANCELLED/NOT_SENT; HUMAN continuation semantics and safe supersession rules
must be durable and concurrency-safe.
P1-R09 — owning CLARIFY -> HUMAN keeps the one-prompt reservation consumed;
only a safe strictly-newer pre-HUMAN AI replacement may release it.
P1-R10 — durable SENDING is a permanent no-POST-retry boundary; current/late
confirmation evidence must be representable monotonically without restoring AI after HUMAN.
P1-R11 — recovery barrier / semantic recovery metadata required by the contract must
be representable fail-closed; stale backup must never infer missing semantic fences.
P1-R12 — one local-filesystem writable episode.sqlite authority; SQL uniqueness,
foreign keys, BEGIN IMMEDIATE/CAS-style transitions, schema attestation and corruption
checks remain enforceable.
P1-R13 — customer text/PII minimization and storage-policy invariants remain intact.
P1-R14 — no new runtime dependency unless a higher-order native/repo/OSS option is
a proven fit and reduces implementation burden without loss of quality.

3. CURRENT IMPLEMENTED/PROVEN REPOSITORY BASELINE

Current FirstLineStateStore schema v3 already provides:
- Node built-in node:sqlite DatabaseSync; no runtime package dependency;
- BEGIN IMMEDIATE transactional writer helper and 5000 ms busy timeout;
- unique source-event identity and deterministic local event_seq;
- one active episode per stream;
- canonical stable-slot provenance and typed constraint latches;
- public_actions with unique (stream_id, prepared_stream_revision);
- one live action per stream for PREPARED/GATING/SENDING/UNCERTAIN;
- PREPARED -> GATING lease claim, SENDING, UNCERTAIN and confirmation primitives;
- atomic CLARIFY reservation and transient reservation attestation;
- explicit schema fingerprint/column/index attestation and v2->v3 explicit migration;
- tests covering the existing v0.7/v3 store invariants.

Current baseline is NOT a complete v0.8 P1 fit. It does not yet implement durable
semantic_origin, DIRECT_HUMAN, NON_ACTIONABLE_ACK, monotonic HUMAN continuation,
complete semantic_scope, reason/template_id/response_locale descriptor fields,
deferred-parent relation, recovery barrier/operator-attention semantic metadata,
or the v0.8 same-revision terminal semantics. Current topology-only public-action
gate may still mark SENDING using v0.7 rules; that gate is outside P1 and must not
be wired as production C6 before P2.

Existing generic src/ops/durable-sqlite-backup.mjs is a proven repository primitive
for encrypted/integrity-checked/fsynced SQLite backup/restore. It is not itself the
P1 state-machine implementation, but it is a likely reusable activation prerequisite.
config/storage-policy.yaml already declares episode.sqlite durable and marks its
required off-host backup REQUIRED_NOT_CONFIGURED; therefore no production schema
migration/activation is authorized by P1 implementation alone.

The additional Chatwoot research does not change P1's bounded semantic-store scope, but it
creates mandatory P2/activation research inputs:
- deployed Chatwoot remains v4.18.0, HEAD 9f920b549c14491a4e587687a3eed5d21c6ccc7d,
  TREE 16432eeeef9153f7aff66be382e04a20e6f5683a;

- current Chatwoot webhook contract uses X-Chatwoot-Signature, X-Chatwoot-Timestamp and
  X-Chatwoot-Delivery; signature verification requires raw request bytes;
- Chatwoot has had webhook payload/format regressions across upgrades, including the
  channel-rendered-HTML/raw-content correction around 4.12.1;
- current docs still warn that conversation_status_changed is not supported when using
  Agent Bot APIs instead of webhooks. Therefore no C6 authority decision may depend on
  receiving that event;
- v0.8's final exact live conversation read remains the authority, so webhook events are
  triggers/hints only.

P2/activation MUST therefore fit-gate and verify, before production activation:
1. one centralized Chatwoot wire anti-corruption adapter; unknown/malformed required shape
   default-denies while additive unknown fields do not crash parsing;
2. HMAC verification over raw body using the exact configured AgentBot/webhook secret,
   bounded timestamp freshness/replay policy, and X-Chatwoot-Delivery dedupe where supplied;
3. source event idempotency remains semantic-store UNIQUE(stream_id, source_message_id);
   ingress delivery dedupe is a separate transport concern and must not become semantic truth;
4. contract fixtures/source-fit tests bound to the deployed Chatwoot version plus the target
   upgrade version before every Chatwoot upgrade;
5. final S2 current-conversation read remains mandatory regardless of webhook order/loss;
6. upgrade runbook: staged source/API fixture verification, migration check, then production
   rollout with rollback; a new Chatwoot version is never assumed wire-compatible.

Already-implemented BabyPark evidence reduces new work: current
`createFirstLineChatwootAuthorityReader()` is already a centralized strict parser for the
authoritative read path; unknown public topology fails closed, and episode.sqlite stores
opaque Chatwoot conversation/message/source identifiers rather than customer phone identity.
Legacy normalizeConversation/evaluateOwnership remain forbidden as C6 authority by v0.8.

WhatsApp BSUID changes are real channel-upgrade risk but are OUT OF SCOPE for Website First
Line C6-P1. They must not widen this bounded stage.


5A. P1 PHYSICAL-STATE SHAPE FROZEN BEFORE CODE

The alternatives decision remains the existing store, but the minimum custom delta is not
authorization for JS-only invariants. Under Agreement §5, state that claims cardinality,
immutability, same-stream linkage or monotonic ownership must be enforced by SQLite
constraints/indexes/foreign keys/triggers wherever SQLite can express it.

P1-S01 — semantic origin is a separate durable relation, not inferred from public_actions.
It has one immutable key `(stream_id, stream_revision)` and exactly one origin kind:
`PUBLIC_ACTION`, `DIRECT_HUMAN`, or `NON_ACTIONABLE_ACK`.
A PUBLIC_ACTION origin requires non-null action_id and relational proof that the referenced
action belongs to the same stream and prepared revision. DIRECT_HUMAN/NON_ACTIONABLE_ACK
require action_id NULL. Duplicate/different origin for one revision is rejected by DB state.

P1-S02 — durable continuation ownership is modeled independently from action lifecycle.
A PUBLIC_ACTION origin may monotonically acquire HUMAN continuation without replacing the
origin or erasing action evidence. DIRECT_HUMAN is already absorbing. The schema must
enforce at most one unresolved continuation owner per stream across live public-action and
HUMAN-owned work; this invariant must not depend only on the current public_actions partial
index because DIRECT_HUMAN has no action row. A dedicated owner relation and/or DB triggers
may be used, but a second AI action while HUMAN ownership is unresolved must be impossible.

P1-S03 — HUMAN continuation terminal evidence is representable without reopening AI.
Store-level terminal outcomes include the frozen `human_takeover` and `ownership_lost`
semantics, while the network/Chatwoot proof that authorizes those transitions remains P2.
Late remote-send proof after HUMAN may append historical confirmation evidence but never
remove HUMAN ownership or restore autonomous AI.

P1-S04 — deferred-parent is a separate immutable same-stream relation, one at most per
accepted customer event. It references the exact owning action/stream with relational
integrity. Event insert + stream revision increment + deferred relation commit is one
BEGIN IMMEDIATE transaction. Reparent/update to another action is forbidden; relation is
scheduling topology only and never C25 causality.

P1-S05 — descriptor/scope v1 is relationally checkable durable provenance, not opaque
unchecked JSON. It must represent descriptor_version=1, reason, template_id,
response_locale exactly uk|ru, source-event coverage and canonical semantic scope:
PRODUCT(product_id,variant_id nullable), CATEGORY(category_id,match_mode), BRAND, STORE,
and MONEY(currency,min_price_minor,max_price_minor).

P1-S06 — MONEY DB checks are fail-closed: both bounds nullable; at least one bound when MONEY
exists; any present bound is a non-negative INTEGER; currency is exactly UAH when MONEY
exists; min<=max when both exist; integer zero is valid. Corrupt/partial/mixed-currency
persisted scope cannot be read as a valid action.

P1-S07 — new v4 tables are STRICT where compatible. Existing v3 tables are not gratuitously
rewritten during migration. Immutability/cardinality rules SQLite cannot express with
CHECK/UNIQUE/FK are enforced with named triggers. Tables/indexes/triggers are included in
the exact sqlite_master fingerprint and column/index/trigger attestation.

P1-S08 — migration is explicit `migrateV3ToV4`, following the proven v2->v3 pattern:
0600 file; foreign_keys/busy_timeout; integrity_check; exact v3 user_version + metadata +
sqlite_master fingerprint + source columns/indexes; one atomic migration transaction;
advance metadata/user_version together; close/reopen and attest exact v4. `open()` on v3
must fail; it must never auto-migrate.

P1-S09 — historical v3 action states remain readable for migration compatibility, including
NOT_SENT/HANDOFF_DONE, but v4 store APIs must not create a same-revision actionable
NOT_SENT escape or use an old terminal state to release continuation ownership while HUMAN
is unresolved. STALE/CANCELLED are allowed only under the frozen strictly-newer/atomic
replacement rules.

P1-S10 — clarification reservation remains consumed through HUMAN escalation and all
post-SENDING outcomes. Only the frozen safe pre-SENDING strictly-newer replacement path may
release an unsent reservation. No migration/default may reset clarification_prompts_sent.

P1-S11 — required store-level tests are part of P1, not deferred:
- duplicate/different same-revision origin rejected;
- PUBLIC_ACTION origin/action stream+revision mismatch rejected;
- origin mutation/deletion through normal store API rejected;
- HUMAN continuation cannot be removed or followed by a second AI action;
- DIRECT_HUMAN blocks AI ownership without any public_actions row;
- deferred parent cross-stream/missing/duplicate/reparent rejected;
- crash/exception cannot commit event without its required deferred relation or vice versa;
- descriptor/scope corrupt combinations fail read/open/transition as applicable;
- UAH zero and nullable-bound MONEY controls; mixed/non-UAH/negative/min>max rejected;
- explicit v3->v4 migration success plus wrong-fingerprint/version/corruption rejection;
- v3 open does not auto-migrate;
- schema fingerprint includes new tables/indexes/triggers;
- concurrent stale writers cannot create two origins/owners/actions.

P1-S12 — P1 does NOT implement S1/S2 Chatwoot reads, webhook HMAC, public POST, scheduler,
operator-attention delivery, C25 routing or deployment. It may expose narrow store APIs that
P2 later calls, but cannot claim external proof it does not own.

Runtime capability check on 2026-10-09:
- development host: Node v22.22.2, SQLite 3.51.2;
- production Chatwoot host: Node v24.20.0, SQLite 3.53.4;
- STRICT tables, partial unique indexes, composite foreign keys and triggers were executed
  successfully on both runtimes using built-in node:sqlite.

This corrects the external review's SQLite 3.47.2 version statement while confirming its
capability conclusion.

6. DECISION-ORDER CONCLUSION

Native Chatwoot capability is not a fit for P1 and may not be patched.
The implemented repository FirstLineStateStore v3 is the correct proven foundation but is
not itself a complete v0.8 fit. No native/repository/OSS/external candidate discovered — including DBOS TS, Restate,
TanStack Workflow, Reflow TS, and the previously scanned workflow engines — closes all P1
requirements while preserving episode.sqlite as the sole semantic owner without adding a
second durable state representation/service, requiring an unreleased backend, or recreating
the required SQL invariants.

Therefore the first proven-fit path is the Agreement order-5 option:

RECOMMENDATION=MINIMAL_CUSTOM_EXTENSION_OF_EXISTING_FIRST_LINE_STATE_STORE
NEW_RUNTIME_DEPENDENCIES=0
NEW_DURABLE_SYSTEMS=0
CHATWOOT_CORE_CHANGES=0

The implementation must be a bounded additive v3->v4 evolution of the existing proven
episode.sqlite state store and must implement P1-S01..P1-S12 above with DB-enforced
cardinality/immutability/linkage wherever expressible, plus focused state/property/race/
crash/migration tests. It must not introduce XState/workflow-engine snapshots as semantic
truth and must not implement scheduler, network send, C25 routing or deployment in P1.
