## 4. SQLite journal alternative matrix (separate from benchmarking-tool selection)

| Required property | **DELETE** (initial candidate, NOT chosen) | **WAL** (plausible alternative, NOT chosen) |
|---|---|---|
| Writer lock / modeled sites | `BEGIN IMMEDIATE` write acquisition + potential reader-blocked **EXCLUSIVE COMMIT**; conditional `K_single_tx=2` with verified `cache_spill=OFF`, no extra sites. | One writer at a time; readers normally do **not** block writer COMMIT, so DELETE-style reader COMMIT site is normally absent. **Do not declare WAL `K=1` without proving busy/recovery/checkpoint sites and selected auto-checkpoint behavior.** |
| Spill, memory, PRAGMAs | `cache_spill` can attempt EXCLUSIVE mid-transaction; OFF removes those spill attempts if verified, but raises dirty-page memory footprint. Verify `journal_mode`, `cache_spill`, `cache_size`, `busy_timeout`, `synchronous` read-back. | Check spill behavior under WAL's own locking; verify `wal_autocheckpoint` and `synchronous` read-back. No assumption that `cache_spill=OFF` solves all WAL stalls. |
| Snapshot/backup B2 and recovery | Standard rollback journal; easier existing B2 normalization/restore, but long read-only backups may block COMMIT. B2 page-step/RPO/restore still unproven. | `-wal` and `-shm` belong to live state; raw copying only `.sqlite` is unsafe. SQLite online backup API can make consistent snapshot if verified; B2 uses sqlite backup/normalization but **WAL source / checkpoint / crash-and-restore behavior is NOT certified**. Checkpoint starvation and long readers can cause unbounded WAL growth. |
| Durability and life cycle | Preserve existing commit durability; journal selection verified **before** v4 DB creation. | If `synchronous=NORMAL`, power-loss durability differs; do NOT silently relax from FULL/default. WAL mode persistent across reopen; page-size changes restricted; checkpoint I/O may occur on the COMMIT thread and create latency. |
| Known version-specific risk | No WAL-reset-specific issue. | Official SQLite WAL-reset bug fixed >=3.51.3; **observed test SQLite 3.53.4 past fix**, actual production bundle must be pinned independently. WAL may still return SQLITE_BUSY for unusual lock/recovery/last-connection cases. |
| Cost/ops/rollback | Fewer live files, easier existing recovery path; may fail 5s budget under DELETE COMMIT reader waits. | Additional disk/sidecar retention, checkpoint ownership, restart/crash/backup runbooks; different operational burden. Cannot move to WAL during this docs-only stage. |

**Decision rule:** compare real synthetic v4 workload, B2 online-backup/read-only overlap and crash/restore in both journal modes, using equivalent verified connections and bounded resource load. Prefer DELETE **first** as merged Design instructs; switch to WAL **only** if DELETE fails evidenced bounded contention/restore gates **and** WAL checkpoint/sidecar durability, backup/restore and deterministic budgeting pass. Neither journal mode is adopted for production by this Scan.

Official SQLite WAL authority https://www.sqlite.org/wal.html (readers/writers, checkpoint auto thresholds, sidecars, rare SQLITE_BUSY, WAL reset version) and https://www.sqlite.org/pragma.html; installed helper source https://github.com/Stanislavikus/babypark-integration/blob/565d8de08fbd8e85598e554cb91e59dfa4f8c1a4/src/ops/durable-sqlite-backup.mjs#L109-L175 and https://github.com/Stanislavikus/babypark-integration/blob/565d8de08fbd8e85598e554cb91e59dfa4f8c1a4/src/copilot/first-line-recovery/profile.mjs#L454-L466.
