## 1. Exact bounded requirements and observations

Existing `src/copilot/first-line-runtime-ingress.mjs` admits authenticated `message_created/incoming/private=false` from the configured account/inbox and checked contact, then an exact Chatwoot authority read, then existing FirstLineStateStore. A signed event failing `incomingTarget()` currently gets HTTP **422**; tests explicitly require it for `outgoing`, `private`, `message_updated`, wrong inbox/account and unsupported sender. Wrong HMAC already gets **401**; missing/unprovable authority or store errors get **503**; changed accepted source topology gets **409**. These are facts from exact PR #128 code, not a proposal to alter all status codes.

Chatwoot v4.18.0 source `9f920b549c14491a4e587687a3eed5d21c6ccc7d`, `lib/webhooks/trigger.rb`: for agent-bot webhook errors on supported message events, a nonretryable HTTP failure can invoke `conversation.open!` if still `pending`, while `assignee_agent_bot_id` may remain assigned and `assignee_id` remain NULL. Retries are native ONLY for 429/500 (`app/jobs/agent_bots/webhook_job.rb`), which logs full `payload.to_json` and can contain customer data. `keep_pending_on_bot_failure` is a real **ACCOUNT-WIDE** native option in `Account#settings`; it disables this status opening for *every* bot failure, including a real unavailable BabyPark authority. This is not verified as a production-ready replacement for HUMAN escalation.

2026-10-11 synthetic rehearsal evidence: existing Website Inbox with `enable_email_collect=true` generated **1 incoming + 2 template** messages (SQL); with configured active synthetic AgentBot, newly created pending/assigned-bot conversation received an incoming message; actual SafeFetch loopback denial in Sidekiq caused `pending→open`, still same AgentBot, `assignee_id=NULL`. Positive signed HTTP 200 case and 42-case matrix remain NOT TESTED: provider execution safety blocked synthetic HMAC-stub creation; no bypass. Four PoC containers safely STOPPED. This proves native failure behavior, **not** that 422 from the real undeployed BabyPark relay was observed against live Chatwoot. All claims about a production Website inbox are contingent on its live read-only configuration, which was NOT inspected.

**Mandatory safety:** no real customer message/body/attachment URL or content-derived digest in BabyPark routine durable state/logs; Chatwoot remains transcript authority; no guessed authority or unsafe customer-facing public action; unknown/unclassified sources deny/fail-closed; no silent automatic `toggle_status(open)` as HUMAN proof; no Chatwoot core/fork patch. Distinguish (a) positive, signed, scope-matched verified **non-customer** event from (b) unknown, malformed, contradictory or lacking authority. A successful ACK for (a) makes **zero customer-turn/action/public-send writes**; for an INTERNAL private row, no public event ledger write is expected. For a public bot/template/human row, however, frozen §29.5–§29.7.2 may **require a bounded existing-store topology event** before or through reconciliation. Do not mislabel a required `SYSTEM_TEMPLATE`/`BABYPARK_PUBLIC_REPLY`/`HUMAN_PUBLIC_REPLY` ledger record as a customer event. A blanket zero-ledger-write ACK for public rows can break S2 complete-history comparison and make subsequent AI turns permanently ineligible; (b) must never be treated as safely ignored. `message_updated` and existing source topology conflicts cannot be declared harmless without frozen semantics. Reliable physical HUMAN/durable operator attention remains separate §29.8.2 contractual work. No production activation as part of this hardening checkpoint.

**Required bounded outcome:** avoid Chatwoot's unnecessary failure transition for positively demonstrated benign bot echo/template/private events while preserving strict authentication, identity, scoped authority, unknown/fail-closed semantics and existing durable idempotency. ## 2.1 Expanded B1 scan after Sonnet challenge — updates, human reply, fast ACK and ledger completeness

**Exact pinned source evidence verified 2026-10-11:** Chatwoot v4.18.0 `app/models/message.rb` lines 140/390 includes `after_update_commit :dispatch_update_event` and `dispatch_update_event` skips only if `previous_changes.blank?`. The `AgentBotListener#message_updated` path checks `message.webhook_sendable?`; the predicate in `MessageFilterHelpers` admits incoming, outgoing AND template without excluding private. Thus a persisted *updated* message in those classes can produce another signed AgentBot callback. The actual update frequency by channel and each changed attribute were **NOT measured**; this is a source-proven path, not a claim every outgoing always updates. Native `Webhooks::Trigger` handles failures for BOTH `message_created` and `message_updated`, so leaving all updated callbacks on 422 risks the same pending→open/SAME_AGENTBOT failure.

**B1 event classes to evaluate together (not seven serial mini-campaigns):** own public bot outgoing, narrow native EmailCollect/greeting/OOO/CSAT templates, private note (including §44 delayed handoff mentions), public HUMAN_USER outgoing, and `message_updated` for each of outgoing/template/private/incoming. A changed incoming customer message needs fresh exact row + immutable v4 source-topology comparison; it is **not** inert. Public human outgoing must preserve/fence native HUMAN ownership and public history, not disappear under generic `2xx ignored`. Native private notes are INTERNAL to `filter_internal_messages=true` and normally do not require a public ledger entry, whereas public bot/template/human rows do.

**Fast ACK without synchronous Chatwoot REST is a PROPOSED ALTERNATIVE, not an authority proof:** HMAC authenticates provenance of the signed Chatwoot trigger, *not* arbitrary current source truth, sender category, message mutation or correct episode ownership. Variant F (provisional) returns `2xx` only for a strictly bounded signed, fully-shaped, target-scoped **provably noncustomer** transport event, with no immediate public send or customer decision; no authoritative source inference is allowed from the payload. The contract still requires a reliable path to reconcile **every public** row (bot/template/human) into the existing event ledger before any S2 public authorization. Current CP1 has no independently proved eventual-writer/reconciliation guarantee for `2xx`-ACKed but unrecorded rows. If it does not, F may reduce Chatwoot failures while causing S2 permanent fail-closed and must be REJECTED for this complete B1 fix. No added durable queue/proxy is allowed by default.

**Conservative variant R (existing API read):** use the current official scoped Chatwoot exact-message reader and v4 event ingestion/identity protocol; distinguish `INTERNAL` private from public `SYSTEM_TEMPLATE`, `BABYPARK_PUBLIC_REPLY` and `HUMAN_PUBLIC_REPLY` with required semantic ownership/reconciliation and idempotency before successful acknowledgment. It has a separate unproven timeout risk: stock Chatwoot `WEBHOOK_TIMEOUT` defaults 5 seconds; external read, database lock and bounded fail-closed paths must fit or stop. The current API reader returns `INTERNAL` without sender/full event, so proving an authoritative private category may require a reviewed native projection, not guessing. Variant R is a **fit candidate subject to correctness/performance proof**, not automatic approval.

**S2 backstop proof (existing exact code, not hypothetical):** `src/copilot/chatwoot-client.mjs#readAuthorizingConversationSnapshot` returns a full filtered Chatwoot PUBLIC snapshot; `src/copilot/first-line-s2-preflight.mjs` compares its row count and every source event to `store.listConversationEvents`, returning `S2_HISTORY_TOPOLOGY_CHANGED` / `S2_HISTORY_TOPOLOGY_UNPROVABLE` on mismatch, before facts/owner/public send; `tests/unit/first-line-s2-covered-text.test.mjs` already checks an additional public row fails. This prevents unsafe public send, but **does not guarantee conversation liveness** when a fast-ACKed public row was never appended. The existing full S2 read is therefore a safety invariant, NOT a license to lose noncustomer events.

**Template classification:** never inspect or persist localized literal template content to decide system origin; existing `classifyPublicWireMessage` proves only narrow `message_type=template`, `sender=none`, known `content_type`, no attachments/unsupported. A template with unknown sender/content type remains UNKNOWN/fail-closed rather than silently accepted. E3 human public reply needs a `HUMAN_PUBLIC_REPLY` topology event and durable HUMAN fence; private §44 notes must not be mistaken for public/customer input or cause bot failure on a safely verified acknowledgment.

**Scan disposition for the expanded subproblem:** no new native AgentBot per-type subscription appeared in the pinned source; the Chatwoot account-wide keep-pending flag still hides genuine failures, not a safe solution. Official REST exact reads and existing v4 ledger remain the only established native/reused components; a direct signed-envelope fast path is **research-only**, with unsolved atomic/reconciliation and trust proof. Therefore the one selected approach remains **KEEP-EXISTING + exact positive event classification/ledger consistency**. No new runtime dependency, Chatwoot patch, parallel stream or production code is approved by this text.
