# AI Working Agreement — babypark-integration

Status: NORMATIVE **only after merge to canonical `main`**; while unmerged, this file is a proposal.

Applies to: repository-wide AI-assisted work in `Stanislavikus/babypark-integration`.

Supersedes: none — this is the inaugural repository adoption; pre-merge review is governed by the first-adoption fallback in §11.

Scope: the **process/governance rules in this agreement are repository-wide** for all AI-assisted work in `Stanislavikus/babypark-integration` (Gateway, Drupal/exporter, Catalog, Knowledge, AI First Line, and future components). Domain rules that explicitly name Chatwoot, customer-facing AI, or another component apply only when that component is in scope. `babypark-b2b` is an absolute repository boundary: never read, import, copy, or reuse its governance, files, examples, or assumptions for this project. Changing that boundary requires a reviewed amendment to this agreement; task-level justification is never enough.

## 1. Requirements first, then implementation order

Before choosing an implementation, identify the complete applicable frozen requirements and invariants for the bounded slice. They define what counts as a fit.

At the beginning of **every bounded development stage involving BabyPark-authored production code or a non-stock implementation choice**, refresh implementation-options evidence before production-code work. Official stock configuration of an already installed product (§1.1), the initial installation of an owner-selected official product under §1.2, and an official stock update under §1.3 are not BabyPark production-code implementation stages and do not trigger an alternatives scan. BabyPark-authored code under §1.4 does. A stage that triggers this scan includes new BabyPark-authored implementation, refactor/hardening, migration/cutover, a non-stock integration change, replacement, or any other stage that adds or modifies BabyPark-authored production behavior. A docs/review-only stage that makes no implementation choice may record that fact, but it never authorizes a later production-code stage to reuse stale alternatives evidence.

The alternatives scan is reproducible gate evidence, not a prose assertion. Record at minimum: UTC scan time; the exact bounded requirements/invariants; sources/catalogs and search queries or equivalent authoritative discovery paths; every owner-named candidate; every materially plausible discovered candidate; exact version/SHA and license/terms where available; PASS/PARTIAL/FAIL per requirement area; integration/operational burden; and the explicit reason each candidate was included, excluded, or deferred. A known owner-named or discovered candidate cannot be silently omitted. If the evidence cannot support the conclusion that no higher-order option is a proven fit, use bounded evidence/PoC or HALT under §9 rather than proceed to custom code.

Before an implementation option is selected for a production-code stage, freeze the complete alternatives-scan evidence: normalize as UTF-8/LF/final-newline, record a SHA-256, and bind the implementation recommendation/decision to that digest. A mutable comment/document identifier is not sufficient. Any material change to requirements, candidate set, search evidence, candidate result, integration burden, or inclusion/exclusion rationale invalidates the prior implementation decision and any dependent pre-code approval until a refreshed scan is frozen under a new digest. The applicable scan digest is required final-gate evidence for every production-code stage; a docs/review-only stage that makes no implementation choice has no scan digest to bind.

Evaluate implementation options in this order:
1. verified native capability of the component/platform in scope. Capability evidence is bound to an explicit component/environment/version tuple. For a production Chatwoot change, the version must match the actually deployed runtime/source for that bounded environment; a planned upgrade version is evaluated separately and cannot be treated as a production-native capability until that rollout boundary is explicit and verified;
2. an **implemented and proven** existing repository capability whose actual behavior already satisfies the requirement. Frozen/normative contracts define fitness and required behavior, but a design-only, planned, or otherwise unimplemented contract is never itself an implementation capability and cannot stop the alternatives scan;
3. real, actively maintained OSS compliant with this agreement;
4. a ready external product/framework/runtime service that is not a qualifying OSS option, but only after §3 architecture-fit establishes its exact commercial/license/usage terms and the owner accepts those terms for this bounded use;
5. custom BabyPark code as the last resort.

A candidate never counts as a fit merely because it exists. It must satisfy all applicable frozen requirements for the implementation choice. For an unchanged vendor-native feature governed by §1.1, the acceptance criteria concern the actual requested functionality, not a new independent security assessment of vendor internals. A non-OSS external product is not a fit when a frozen/owner requirement demands free/open-source commercial use, when its required capability is behind an unacceptable paid/usage/product-count gate, or before the §3 architecture-fit + owner acceptance required above.

The active owner engineering rule is preserved exactly for the ready-solution-vs-custom boundary: when a **free ready solution** (OSS or otherwise permitted external product) can be integrated faster than writing the equivalent custom production code, without loss of quality, and closes the need, custom production code is forbidden. Use the official stock function. Custom code is reached only when that function does not exist or the official way is very inconvenient or slow, and then only as separated code under §1.4. Conversely, an OSS/product candidate that meets functional requirements but is demonstrably slower/higher-burden to integrate or loses required quality does not automatically win merely because it is ready-made; record that delivery/quality result and continue the decision. If that comparison is materially uncertain, use a bounded evidence/PoC step or halt under §9 rather than guessing in favor of either a ready solution or custom code.

Stop at the first option in the order above that is a proven fit under those rules.

**Chatwoot core patch rule:** core patches, forks, or changes that block normal Chatwoot upgrades are rejected in this repository. They cannot be authorized by a task-level exception or ordinary owner approval. Reopening that boundary requires a reviewed amendment to this agreement.

### 1.1 Official stock vendor functions — bounded functional acceptance only

**Determine scope, not vendor vulnerabilities.** **BabyPark-authored** means code BabyPark writes: a repository module, script, custom node package, patch, fork, or a workflow node whose body is BabyPark-written code, such as an n8n Code node. A workflow, automation, credential, or webhook composed only of official nodes, official fields, and official expressions is stock configuration.

Classify the requested work by what BabyPark actually changes:
1. **STOCK-NATIVE**: turn on or configure a documented, unmodified feature of a vendor product already installed at BabyPark, using official controls, SDK, API, examples, nodes, adapters, credentials, or webhooks, and adding no BabyPark-authored code. Official configuration that connects two already installed products is STOCK-NATIVE of those products. Official n8n nodes used with Chatwoot's official API are this class. Customer email, conversations, identity, or other data flowing through that official feature does not move it into class 2. A version upgrade of the feature follows §1.3. Apply the four-step functional path below to first activation and to a later functional check of the configured path.
2. **BABYPARK-OWNED / MATERIALLY EXTENDED**: BabyPark-authored code, including a configuration-only change of BabyPark-authored logic that alters its customer-data scope, connectivity, or production use. Official stock configuration in class 1 is not this class. Apply §§1, 3 and 1.4 to the BabyPark-authored change. Do not audit unrelated unchanged vendor code, and do not treat the official nodes beside the custom code as custom code.
3. **NEW INDEPENDENT PROVIDER**: the first adoption of a separate external product, including adoption through its official connector. An official connector does not make the new product a native feature of a different product that is already installed, and it does not require a custom connector. When the owner has studied the official functions and terms of use, they suit the requested use, and every §1.2 condition holds, the initial installation uses §1.2 on the production target. If an install-moment condition fails, stop that install. A missing operator protection is reported as that missing protection and is not turned into an architecture-fit study. If the official functions or terms do not suit the request, return to the §1 decision order for that unmet need. After the product is installed, its official features are class 1.

**Only four steps for STOCK-NATIVE:**
1. For **first activation** of a stock feature already installed at BabyPark (not a version upgrade under §1.3), with the owner's explicit bounded live-test permission configure that feature **on the actual production target**, after verifying the narrow operator backup/rollback and affected-channel scope. Agree and test only the **specific real-world working path** there, using an authorized test contact/conversation where customer delivery is involved; do not activate the feature for unrelated customers as a side effect. A DEV/rehearsal PoC or other pre-production functional test is **not required** and must not be imposed as a prerequisite. Do not enumerate hypothetical scenarios, perform vendor security testing, or inspect vendor code.
2. If that path works as agreed, record exactly: **«ПРОВЕРЕНО: PASS. Готово к запуску в проверенной конфигурации»** with the vendor version/configuration, actual observed result and the supported rollback procedure. **This completes technical acceptance.** Activation requires the owner's permission; no follow-up investigation or added tests of the vendor are required.
3. If an actual failure occurs **during this functional check**, record the expected and actual outcome. Investigate only how to correct **that observed failure**, within the affected function and official integration mechanisms. Do not extend the inquiry to hypothetical vendor flaws, unrelated functions or attack scenarios.
4. After correction, repeat **only the affected working path**. If it passes, record the same PASS statement and proceed to the owner's activation decision. If it still fails, report the concrete failure; do not claim PASS.

**Explicit prohibition.** For STOCK-NATIVE acceptance, and equally for a §1.2 installation and a §1.3 stock update, do not hunt for vendor vulnerabilities, audit vendor security/source, run penetration or red-team tests, research hypothetical attack chains, demand evidence that the vendor has no vulnerabilities, or commission other models to do so. BabyPark studies stock functions and terms of use. BabyPark does not security-test other people's products. This cannot be reintroduced through labels such as `risk assessment`, `privacy review`, `architecture fit`, `HEAVY`, `source-supported`, `independent review`, `unknown evidence` or equivalent terminology. A suspicion based on code or imagination is **not an observed functional FAIL**, and cannot invalidate a verified PASS or create a new acceptance requirement.

This provision does not instruct BabyPark to ignore an **actual** harmful incident observed in normal work. It is not a new vulnerability test. The specific stock-vendor acceptance rule takes precedence over generic extra-testing/fit/review/halt language in §§1, 2.0a, 3, 7, 9 and 13 insofar as it would require vendor security/privacy re-review or extra vendor tests after a STOCK-NATIVE, §1.2, or §1.3 stock PASS. Separately applicable standing BabyPark-owned operational duties are not themselves a vendor test. Governance amendments themselves and BabyPark-owned implementations retain their separate review and merge procedures under the currently authoritative Agreement.

### 1.2 STOCK-DEPLOY — production-first official product installation

**Owner policy: study official functions and terms of use, then install and use the product.** This initial-installation path is available for the first installation of an owner-selected product at BabyPark only when **all** of the following are true at the installation moment: (a) the exact maintained official release/image is installed unmodified through official documented install/configuration tools; (b) no BabyPark-authored runtime, adapter, data transformation, or customer-decision code is added; (c) the new service starts **inactive, private and isolated**, with no real customer content, no credentials of another production service, no outbound customer actions, no public editor or webhook, and no activated workflow; (d) existing production services, including Chatwoot and Viber, are not modified or restarted to make the new service work; and (e) the bounded operator preflight below is achievable. These conditions describe the installation moment. A later official stock configuration under §1.1 does not erase a completed installation and does not send that configuration back through §§1/3. Failure of an install-moment condition stops that install action. A missing operator protection is reported as that missing protection. It is not converted into an architecture-fit study.

**Study official functions and terms of use. Do not security-test the vendor.** Before the first deployment, study the official documentation of the stock functions BabyPark wants and the vendor's terms of use, license, and permitted commercial use, in enough detail to decide whether they suit this use. If they suit it, install the official product and use those functions. The result to reach is a working product. This study is required. It is not a functional test, and it is not a vulnerability hunt, source audit, penetration test, or commission to another model to do that work. BabyPark does not security-test other people's products. **No pre-install functional gate.** Do not require a DEV or rehearsal PoC, a repeated import test of workflows already checked for this same release, an alternatives matrix, or a functional test of the unchanged product before the owner-authorized installation. A completed study or a completed check of the same official release stays reusable and is not redone. A result for a different version is historical only and does not prove the version being installed; that version is accepted by the functional check on the target after installation. A concrete incompatibility that the official documentation states for a function BabyPark needs is handled by official configuration or by reporting the gap.

**One short install record before the first production write** is sufficient; it is not a full architecture-fit/alternatives-scan package. Record: owner request and exact official version/image digest; the studied stock functions; terms/license and whether the permitted use suits the request; target server and explicit owner **STOCK-DEPLOY GO**; the new service's own paths and its own credentials (names/locations only, never values); local-only listener/network and no-customer-data state for this installation moment; independently restorable state, key and backup; resource ceiling and live stop thresholds; the exact official start/stop/rollback commands; and the exact tracked configuration/storage registration. Verify only operator-controlled essentials that protect existing production: restorable current service backups, permissions/secret absence from Git, no unexpected Docker/firewall/port effects, storage-policy declaration before writes, available stop/rollback, and sufficient baseline resources for the bounded cap. These are preflight safety checks, **not vendor functional tests and not a security audit**. If they cannot be verified, stop before the first production write and report the concrete missing protection rather than starting a research campaign.

**Test the actual installation on production.** With the owner's separate explicit installation GO, install the unmodified vendor through official commands on the selected target, preserving existing services. Start only the private/inactive instance with bounded CPU/RAM and verified local access; measure actual runtime memory/pressure and existing service health. Check the one agreed functional startup path, any exact-version storage/retention behavior relied upon, and a disposable same-version backup/restore with a dummy key/credential as applicable **there**, using synthetic data only. Do not connect the live customer path for this check. A real functional FAIL or harmful resource/network effect => stop only the new service, record expected vs actual, use a supported stock correction, and repeat only that failed check. If a mandatory condition cannot be met with official options, stop; never fill the gap with unapproved custom code. At PASS the installed product is a functioning private production service, not a permanent proof-of-concept. It stays private until a separate §1.1 official stock configuration has passed on the authorized path. The owner then decides whether to activate that path.

**No duplicate review machinery for stock-only changes.** A STOCK-DEPLOY-only package consisting of vendor Compose/systemd/service settings, documentation, and additive storage-policy registrations uses the §7.0a focused stock-install exception; no full §1 alternatives matrix, SHA-bound non-stock architecture fit, root-wide code test suite, vendor internals audit, or HEAVY review of vendor internals is required merely because a ready-made executable or vendor-owned database is new. Exact release/config identity, targeted syntax/storage-policy validation, the owner's install GO and the live acceptance record remain required. BabyPark-authored code uses §1.4 and its ordinary review.

**Boundary after installation.** The install GO proves that the private product runs. It does not by itself turn on customer delivery. When the owner wants the installed product to perform its job, the next step is official stock configuration under §1.1: official nodes, official APIs, official adapters, official credentials, and the official webhook that integration documents, with no BabyPark-authored code. Accept that configuration by the four-step functional path on the production target. Where the path can deliver to a customer, use an authorized test conversation and do not expose unrelated customers. Passing that path does not reopen the installation as a §3 architecture-fit campaign, an alternatives scan, a vendor security audit, or a HEAVY review of vendor internals, and it does not classify the official nodes as custom code. Official n8n workflows connected to Chatwoot through official nodes and Chatwoot's official API are this stock path. Installation of n8n must not leave that path blocked behind a custom-integration campaign.

These duties stay in force on that path: the owner's activation permission; §2.0a operator duties; §4 transcript authority, dynamic-fact freshness, and fail-closed sending; the applicable frozen domain contract for money, price, and customer sends; no secrets in Git or logs; no Chatwoot core patch; no change to Viber or to an unrelated live channel as a side effect of the new path. Use official settings so customer content is not routinely copied into an extra store. If the official product cannot perform the required function without persisting customer content contrary to §4, stop and report that gap. Do not audit vendor source, and do not fill the gap with custom code unless the owner separately approves §1.4. BabyPark-authored decision logic remains §1.4 even when official nodes surround it. The official nodes remain stock. Preserve server-handbook documentation after any accepted installation. An unmerged proposal of this section has no authority under §11.

### 1.3 Official product updates

Before applying an official update, read the vendor's update requirements, release notes, and the terms of use that apply to the functions BabyPark uses.

**No restriction.** When those documents state no restriction on the used functions or on the permitted use, back up the product by the official backup procedure and apply the official update on production. Then check the functions BabyPark uses. PASS continues operation. An observed failure is corrected by an official fix or by restoring the backup, and only the failing function is rechecked.

**Doubt.** When those documents restrict a used function, change behavior BabyPark relies on, change the permitted use, or leave it unclear whether the used functions remain valid, do not update production on that basis. Automatically apply that exact official release on the test installation only. Check the functions BabyPark uses and the native functions that release actually changes. PASS: back up production and apply that same tested release to production as a controlled update. FAIL: use an official fix or rollback, and recheck only the failing function. Production does not change because the test installation changed. If a test installation does not exist yet, use or create one for this doubtful update. A test installation is not a prerequisite for the first installation under §1.2, and it is not a prerequisite for a no-restriction update.

**Unattended production auto-update is forbidden.** An updater must not move production without the requirement reading and the backup. A stock update does not require a new alternatives-scan digest, an architecture-fit note, a vendor security audit, a repeated study of unchanged functions, or a HEAVY review of vendor internals. It does not authorize an uncontrolled customer send, storage of transcripts outside §4, or an unrelated change to Chatwoot or Viber. An official setting that the updated product's documentation requires in the other already installed product, for a stock connection already accepted under §1.1, is part of this update's functional check. It is not a core patch and it is not a new fit campaign. Before the production write, use the official backup and rollback procedure, confirm the target identity and that required durable state can be restored, and confirm that other running services stay reachable. A known active incident or a missing essential backup blocks only the affected rollout.

Separated BabyPark-authored code under §1.4 stays outside the vendor image. The official update runs against the unmodified product and does not rewrite that code. The update instruction lists the separated code so the update proceeds without rediscovering it. This section is operative only after this amendment is merged under §11.

### 1.4 Separated custom code — last resort

Custom BabyPark code is allowed only when the required function has no official stock implementation, or the official way is very inconvenient or slow and the owner accepts custom code after that comparison is shown. A free official function that meets the need with ordinary configuration effort is the implementation. The owner makes the custom-code choice. An uncertain comparison halts under §9 for that choice. An agent does not invent a custom replacement while an official function fits.

When custom code is approved, keep the stock product updatable under §1.3 without editing that code:
- place it outside the vendor image and outside vendor core, at an official extension point, in a sidecar, or in a BabyPark repository module;
- do not patch or fork Chatwoot core;
- record it in the update instruction in the existing on-server handbook at `/var/backups/babypark-integration/operations/customizations/` on chatwoot-fra1-01, and keep a Git-tracked pointer that contains no secrets. The record states the purpose, the location, the stock function it could not replace, what the official update must leave untouched, and any re-apply step at an official extension point.

An n8n Code node, or any node whose body is BabyPark-written script, is this custom code even when official nodes surround it. Those official nodes remain §1.1. The custom node is recorded and separated so an official product update does not become a redevelopment of the script. §§1, 3, 6 and 7 apply to the custom code. They do not expand into a security audit of the surrounding stock product.

## 2. Document authority — discover, classify, fail closed

List `docs/` fresh at the start of repo work. Filename prefixes do not make a document normative.

Every new or modified documentation file that may participate in gating work must state, near its top, enough metadata to resolve:
- `Status`: NORMATIVE / EVIDENCE / HISTORICAL / RUNBOOK (an existing explicit phrase such as `FROZEN` or `IMPLEMENTATION EVIDENCE — NON-NORMATIVE` is equivalent);
- `Applies to`: the bounded system/slice or `repository-wide`;
- `Supersedes`: exact predecessor(s) or `none`.

Authority resolution order applies to the **merged canonical tree**:
1. explicit in-document status controls;
2. citation from an already normative document determines **applicability**, not status;
3. otherwise the document is **UNCLASSIFIED** and cannot authorize behavior until classified.

An unmerged branch-local addition or amendment that declares itself `NORMATIVE` / `FROZEN` is still only a **proposal** during review. The target/base merged contract remains authority until merge. A proposed new contract with no predecessor is governed by this agreement plus the existing applicable merged contracts and cannot authorize its own review or waive a base invariant.

Filename prefixes never confer authority. Explicit EVIDENCE / NON-NORMATIVE / HISTORICAL status always beats a filename family. Therefore `AI_FIRST_LINE_C3_TRACEABILITY.md`, which self-declares implementation evidence/non-normative, cannot become normative merely because it starts with `AI_FIRST_LINE_`.

Legacy docs merged before this Agreement's inaugural adoption do not need mass edits merely to exist, but their gating status is deterministic:

- an explicit legacy `FROZEN` status is treated as NORMATIVE for the bounded design/acceptance content it freezes;
- an explicit `IMPLEMENTATION EVIDENCE — NON-NORMATIVE`, `EVIDENCE`, `HISTORICAL`, or `RUNBOOK` status maps to that declared non-authority class;
- every other pre-adoption status form is `LEGACY-UNCLASSIFIED` for gating authority, including bare `CURRENT`, `CURRENT + PLANNED`, `CURRENT production authority`, `CURRENT production read contract`, `IMPLEMENTED ... / NOT DEPLOYED`, `MERGED-CANDIDATE`, `DRAFT`, `PLANNED`, and similar mixed lifecycle prose. Words such as `current`, `production`, or `implemented` never elevate authority by themselves.

A LEGACY-UNCLASSIFIED document may be consulted as background evidence but cannot authorize a gating decision. If a future change needs it as authority, first merge a bounded classification/governance change that adds the standard Status / Applies-to / Supersedes metadata without relying on that same document for its own authority. The consuming feature/change starts its gate only after that classification is present on canonical `main`. A branch-local same-change classification remains a proposal and cannot bootstrap authority for the implementation beside it.

Every gating review must be able to classify each document it relies on exactly once. Ambiguous status, applicability, or supersession halts fail-closed under §9.

`docs/AI_WORKING_AGREEMENT.md` is the single repository source of process/governance authority once merged to `main`.

A correction/delta must be merged into its base normative document in the same change. Never leave a second standalone "also normative" delta file behind.

### 7.1 Exhaustive adversarial review protocol

Do not default to a serial "find one blocker → fix → review again" loop. The exhaustive inventory/fix/verification discipline below applies to **both** risk tiers; risk tier changes the finite closure rule, not whether the applicable surface is inspected.

**Inventory pass.** On one exact pinned HEAD/tree/base, inspect the complete applicable contract and implementation, continue after the first finding, and cluster permutations into independent root-cause classes. Cross-check precedence/gate interactions, authority/read provenance, identity/cardinality, clarification continuation, locale/presentation, typed payload boundaries, durable restart behavior, and freshness/send semantics where applicable.

**Batch fix.** Fix the complete known blocker inventory coherently inside the same bounded campaign. Do not move the reviewed HEAD while an inventory/verification pass is running; if it must move, cancel that pass and restart on the new exact tree.

**Verification pass.** On the new exact HEAD/tree/base, verify every prior blocker and continue searching the whole applicable surface for additional independent blocker classes. If any blocker remains, classify it, batch-fix the complete known set, and repeat verification.

**STANDARD finite closure.** For a correctly classified STANDARD change, one exhaustive exact-tree verification bound to the unchanged required-verification-manifest SHA-256 that reports ZERO BLOCKERS closes the blocker gate. This is permitted only because the change is composing already-proven primitives and the classification evidence is part of the gate. A newly discovered HEAVY condition invalidates that closure and triggers HEAVY review.

**HEAVY finite closure.** When an exhaustive verification first reports ZERO BLOCKERS, run one separately triggered **run-independent exhaustive confirmation** on the **unchanged exact HEAD/tree/base, unchanged governance authority tuple from §2.1, and unchanged required-verification-manifest SHA-256 from §7.0a**. The blocker gate closes only if that confirmation also reports ZERO BLOCKERS. The confirmation does not recursively require a third clean pass.

For this agreement, **run-independent** requires **context isolation**, not merely a second run ID. The confirmation context receives the pinned campaign basis/governance authority (or, for inaugural adoption, the complete first-adoption invariant manifest + bound snapshot digest), **read-only access to the complete exact repository tree at the pinned HEAD**, the complete normalized frozen required-verification-manifest bytes + their SHA-256, the artifact/diff, all applicable contracts, and any external/runtime evidence that the frozen manifest itself requires the confirmation to inspect. The confirmation must independently inspect changed-surface classification, command completeness, relevant implementation interactions and cited factual claims; a digest of unseen bytes or a diff without the surrounding exact implementation is insufficient. To preserve independence, it must **not** receive the first review's clean conclusion, transcript, finding summary, reasoning, or a same-conversation continuation that can anchor the second judgment.

A genuinely separate reviewer/model/service in a fresh context qualifies. The same service qualifies only when a clean isolated context can be proven. If the normal PR-review surface necessarily exposes the first review conversation, use a separate clean review context (for example a temporary Draft review-only carrier) or HALT until an isolated reviewer is available. Replaying, reusing, re-labeling, or following up in the same review conversation is never independent.

The **campaign basis** remains the exact campaign HEAD/tree/base/governance tuple. A review-only carrier's branch head must equal the campaign HEAD and its base must equal the campaign base; it accepts no implementation commits. A review service may internally materialize a synthetic merge/check commit instead of executing directly on the branch-head SHA. That transport commit does not invalidate confirmation **only if an equivalence proof is recorded**: the carrier branch head still equals campaign HEAD; carrier base still equals campaign base; the synthetic commit tree equals the exact campaign tree; its parent/provenance graph is exactly the validated base + campaign HEAD (or a tool-equivalent construction proven to add no content); and there is zero tree delta between synthetic review artifact and campaign tree. Record the review service's reported commit plus this mapping when available. If any equivalence fact is missing, mismatched, or unverifiable, the confirmation is invalid and the gate remains open.

If a HEAVY confirmation finds a blocker, or the exact HEAD/tree/base/governance basis changes, batch-fix/re-pin as applicable and restart the HEAVY verification cycle.

One clean pass remains evidence rather than universal proof; the tiered finite rules above define when that evidence is sufficient for this repository's merge gate without imposing HEAVY confirmation on already-proven composition work.

### 7.2 Unchanged stock vendor functions — technical acceptance ends at functional PASS

### 7.3 Known vendor-owned residuals in non-STOCK-NATIVE integration work

**Scope.** §7.3 applies to BABYPARK-OWNED / MATERIALLY EXTENDED work and to a new-provider adoption that is not on the §1.2 path, including configuration-only changes of BabyPark-authored logic. It does not apply to STOCK-NATIVE official configuration, a §1.2 installation, or a §1.3 stock update, including when customer data flows through the vendor's own official feature. It cannot restart a vendor security review after those stock paths pass.

**Purpose.** BabyPark integrates and operates vendor products; it does not maintain their internal source code or promise they are defect-free. The goal is useful, maintainable releases with proportionate customer safeguards, not perfection or endless repair of upstream code. A verified defect in unchanged vendor-owned implementation is classified separately from a BabyPark-created implementation/configuration defect, using the product/version, affected path and concrete evidence. Vendor ownership does not remove BabyPark's responsibility for deciding what to activate.

**One bounded search.** Collect the entire known vendor-defect inventory for a bounded release. Reuse existing evidence and perform one consolidated scan of upstream fixes, stock configuration, official workarounds and maintained ready-made options under §§1–3. Allow **no more than one additional independent-model investigation for that complete inventory**, never one per defect. If no clearly suitable remedy is found, **stop researching upstream remediation on the unchanged evidence and make a release-risk decision**. No requirement to fix all vendor bugs, repeatedly review hypothetical consequences, invent defenses, create substitute products or redo successful integration tests. Material new evidence, a relevant vendor release or separately approved scope change may reopen only the affected issue. This limit does not cap §7.1 verification of BabyPark-owned changes.

**Remediation boundary.** Apply a mitigation within the campaign only if it uses official configuration/SDK/API/examples or maintained supported connectors, has obvious bounded verification and rollback, preserves required existing functionality, and has no material new risk. Never modify/fork/cherry-pick Chatwoot core, and never start custom production code just to repair vendor internals. If these conditions are not demonstrated in the one investigation, do not attempt remediation.

**Assess actual incremental risk.** Compare credible consequences *with the proposed feature enabled* against the *actual currently operating production baseline*. Consider realistically reachable public API paths, affected data, actual controls, recoverability and applicable legal/privacy requirements. Label material claims VERIFIED, SOURCE-SUPPORTED, INFERRED or UNKNOWN. Neither multiply an ordinary defect into the worst imaginable chain without causal evidence nor demand proof that all attacks are impossible. Tools/scripts, intentional inputs or repeat attempts do not automatically render a realistically reachable vulnerability theoretical. One bounded, adequately supported decision is enough; do not endlessly investigate speculative mitigations.

Classify each known vendor-owned residual into exactly one level:

1. **ROUTINE VENDOR RISK.** Limited, reversible or operationally manageable issues without credible material cross-customer confidentiality, unauthorized financial action or substantial irreversible data harm (e.g., occasional duplicate messages). Eligible for **owner-authorized release** with brief documentation and proportional incident response. No mandatory new monitoring service, dedicated security audit or custom code.
2. **MATERIAL MANAGEABLE VENDOR RISK.** Potentially significant consequences, credibly bounded by **already existing, effective** protections and achievable incident response/rollback while mandatory security, legal and privacy conditions remain met. Eligible for **explicit scoped owner acceptance**. Staff advice and detection after an incident must not be portrayed as preventing unauthorized disclosure.
3. **UNCONTROLLED MATERIAL EXPOSURE.** Reproduced or strongly source-supported and realistically reachable unauthorized access to another customer's non-public data, unauthorized financial action or substantial irreversible damage, **with no effective applicable protection**. **HOLD only the affected feature/exposed path** until a supported upstream fix or native configuration removes that exposure; do not halt unrelated live channels or development. Ordinary owner risk acceptance cannot waive mandatory protection requirements in §§2.0a, 3 and 4.

Unknown evidence is neither proof of safety nor proof of the worst case. If an essential safety premise remains UNKNOWN after the bounded check, HOLD only the affected activation/path under §9; do not automatically launch another investigation. STOCK-NATIVE configuration, §1.2 installation, and §1.3 stock updates are excluded entirely, and a defect in one non-stock channel does **not** automatically require auditing others absent specific evidence of a shared vulnerable path.

**Review and release gate.** Use BABYPARK BLOCKER (our code/configuration or unmet frozen requirement), VENDOR DEFECT — DECISION PENDING, and VENDOR RISK — OWNER ACCEPTED. An eligible ROUTINE or MATERIAL MANAGEABLE vendor residual is not automatically a BabyPark-code BLOCKER for §7/§7.1 ZERO BLOCKERS closure: reviewers still inventory it and verify evidence and classification, but need not fix vendor source. The defect remains DECISION PENDING until explicit owner acceptance on the exact version/feature/release basis, possibly in the final authenticated §7 GO. No owner acceptance means no merge or activation. An unresolved BabyPark blocker, unmet frozen requirement, UNCONTROLLED MATERIAL EXPOSURE or mandatory privacy/legal/security failure can **never** be relabeled as accepted vendor risk. Risk acceptance never means FIXED.

Prepare **one concise release decision record** (not a new audit): vendor/version/upstream issue, observed versus inferred impact, incremental exposure, rejected stock remedies and rationale, existing controls, practical incident/rollback action, risk level, and RELEASE WITH ACCEPTED VENDOR RISK or HOLD. The owner's explicit acceptance identifies exactly which feature, version, consequences and record are approved; never silently or generically accept future defects.

**Operational register and upgrades.** Record accepted material vendor risks in a canonical Git-tracked docs/ register and cross-reference the protected on-server handbook at /var/backups/babypark-integration/operations/customizations/ on chatwoot-fra1-01. Record upstream source, affected version, owner decision, incident response and short targeted regression. Do not store customer texts/secrets or create a second normative governance file on the server. At the first and **every subsequent relevant vendor upgrade** until closure, inspect the actual shipped fix and run only the affected synthetic regression; mark FIXED / PARTIALLY FIXED / STILL OPEN / UNKNOWN. Release notes alone are insufficient. No new investigation for an unchanged residual; material increase in impact requires a fresh owner decision.

**Authority.** This provision only takes effect after the ordinary §11 review and merge into canonical main; it cannot self-authorize release, core patches, or waiver of mandatory law/privacy/security requirements.
